# QA AI Agent

QA AI Agent — мощный Telegram-бот для автоматизации процессов тестирования (QA) и роботизации рутинных задач (RPA).

Бот интегрирован с искусственным интеллектом для генерации автотестов «на лету» и использует невидимый браузер (Playwright) для выполнения E2E-сценариев и выписки страховых полисов прямо через UI. Для стабильной работы тяжелых UI-тестов реализована встроенная система очередей (Queue), предотвращающая перегрузку памяти (OOM) при множественных одновременных запросах.

---

## Основные возможности

| Возможность | Описание |
|---|---|
| AI-генерация тестов | Автоматическое написание и запуск Playwright-тестов по текстовому описанию фичи |
| Регрессионное тестирование | Пакетный запуск сгенерированных тестов и отслеживание статусов (Сломано / Починено) |
| Excel & PDF отчёты | Генерация наглядных отчётов по результатам прогона тестов |
| Анализ багов | AI-инспекция логов ошибок с подсказками по их исправлению |
| API-интеграция | Быстрый поиск и получение данных по страховым полисам (ОГПО, НС, МСТ) через REST API |
| RPA (Web Automation) | Автоматическая выписка полисов через веб-интерфейс (эмуляция действий пользователя) со скриншотами |
| Умный парсинг (OCR) | Обработка загружаемых документов (удостоверения, паспорта, техпаспорта), включая альбомы из нескольких файлов |
| Очередизация сессий | Глобальная очередь задач (Queue) для параллельного использования бота множеством тестировщиков без падения сервера |

## Развёртывание (Deployment)

### Вариант 1. Автоматический деплой на VPS (Ubuntu 22.04)

Если вы поднимаете бота на чистом сервере, достаточно запустить bash-скрипт:

```bash
bash deploy.sh
```

### Вариант 2. Ручная установка (Local / Custom VPS)

Для самостоятельного развёртывания без использования `deploy.sh`:

**1. Склонировать репозиторий:**

```bash
git clone <url_вашего_репозитория>
cd qa-ai-agent
```

**2. Инициализировать git (если необходимо):**

```bash
git init
```

**3. Настроить переменные окружения.**

Скопируйте пример файла конфигурации и заполните его своими данными:

```bash
cp .env.example .env
```

> **Внимание:** обязательно укажите токен бота, AI-токен, ваш Telegram ID для доступа и креды от тестовых стендов (см. таблицу ниже).

**4. Сборка и запуск через Docker.**

При первом запуске рекомендуется использовать `--build` (или `--no-cache` для полностью чистой сборки):

```bash
docker compose up -d --build
```

При повторном запуске флаг `--no-cache` можно не указывать — для более быстрого деплоя.

**5. Проверка логов.**

Убедитесь, что контейнер успешно стартовал и браузер инициализировался:

```bash
docker compose logs --tail 50 -f
```

## Команды бота

Бот поддерживает маршрутизацию команд в стиле консольного интерфейса, а также использует многошаговые сцены (WizardScenes) для сбора данных.

### Тестирование и AI

| Команда | Назначение |
|---|---|
| `/test <url> <фича>` | Сгенерировать AI-тест (Playwright), запустить его и выдать отчёт |
| `/test list` | Показать список всех сгенерированных тестов (ID) |
| `/test run <ID>` | Запустить конкретный тест по его ID (например, TC-001) |
| `/test retry <ID>` | Перезапустить только упавшие шаги в тесте |
| `/regress [url]` | Запустить регресс-прогон всех последних тестов |
| `/checklist <url> <фича>` | Сгенерировать чек-лист проверок для фичи |
| `/investigate <лог>` | AI-анализ причины падения теста |

### Работа со страховыми продуктами (API)

| Команда | Назначение |
|---|---|
| `/policy ns list` | Получить список полисов НС по API |
| `/policy mst <ИИН>` | Найти полисы МСТ по ИИН пользователя через API |
| `/policy ogpo <номер>` | Получить детали конкретного полиса ОГПО |

### RPA (выписка через Web и Playwright)

Модуль RPA поддерживает систему очередей. Если бот уже выполняет E2E тест для другого пользователя, ваш запрос будет поставлен в ожидание.

| Команда | Назначение |
|---|---|
| `web ogpo phis` | Оформление полиса ОГПО для физических лиц. Поддерживает загрузку документа техпаспорта, OCR и ЕСБД |
| `web ogpo legal` | Оформление полиса ОГПО для юридических лиц. Умный перехват альбомов из Telegram (ожидает загрузку 2 файлов сразу: лицевая и оборотная сторона техпаспорта) |
| `web mst [premium] [цель] [возраст] [1–5]` | Выписка полиса МСТ / МСТ Premium через сайт (подробнее ниже) |
| `web ns [стандарт\|спорт] [взрослые\|дети] [1–10]` | Выписка полиса НС через сайт (подробнее ниже) |
| `web ns ошибки` | Проверки формы НС на неправильных данных (N01–N09), без выписки |

### Тестирование страховых продуктов (НС и МСТ)

НС и МСТ — продукты одного уровня: у каждого своя папка, а то, что у них общее, лежит отдельно.

| Где | Что |
|---|---|
| `src/insurance/` | общее для всех продуктов: вход на сайт и наблюдение за страницей (`flow.js`), общий путь покупки — выписка с защитой запроса, договор, карточка, ЕСБД, снимки (`purchase.js`), модель проверок и общие проверки (`checks.js`), вызовы NDP API (`api.js`), журнал заявок (`journal.js`), отчёт в Telegram (`report.js`) |
| `src/ns/` | НС: форма и проверки ошибок формы (`flow.js`), команда и сценарии (`cases.js`), проверки НС (`checks.js`), прогон `api ns` (`api.js`) |
| `src/mst/` | МСТ: форма (`flow.js`), команда, туристы и справочники (`cases.js`), проверки МСТ (`checks.js`) |
| `src/bot/handlers/` | `nsHandler.js` и `mstHandler.js` — команды продуктов; `insurance.js` — общий запуск прогона, отчёт и журнал |
| `fixtures/` | `insurance.json` — тестовый клиент и известные проблемы общих частей сайта (ЕСБД, карточка, стенд); `ns.json` — правила, тарифы и известные проблемы НС; `mst.json` — известные проблемы МСТ |

Новый продукт добавляется своей папкой `src/<продукт>/` (форма — наследник `PurchaseFlow`, набор проверок `*_KIT` для `runPurchase`), своим обработчиком и `fixtures/<продукт>.json`; общий код при этом не меняется.

#### НС

Две группы команд: `web` — через сайт в браузере, `api` — напрямую в сервер. Команда `test` целиком относится к AI-генерации тестов.

| Команда | Что делает | Полис на dev |
|---|---|---|
| `web ns` | Стандарт, взрослый, 1 человек | 1 |
| `web ns спорт дети 3` | Выписка с заданными программой, категорией и количеством | 1 |
| `web ns ошибки` | Проверки формы на неправильных данных (N01–N09) | нет |
| `api ns` | Калькулятор (A01–A22) и выписка через API (I01–I18) | 4 + ошибочно принятые отказы |
| `api mst` | МСТ: калькулятор (MA01–MA30) и выписка через API (MI01–MI18) | 5 + ошибочно принятые отказы |
| `web ns журнал` / `api ns журнал` | Незавершённые заявки этого канала | — |
| `web ns снять <id>` / `api ns снять <id>` | Ручное снятие блокировки | — |
| `web ns помощь` / `api ns помощь` | Подсказка | — |
| `web ns тесты` / `api ns тесты` | Список всего, что проверяет команда, простыми словами; для `api ns` — ещё и какие сценарии сейчас пропускаются | — |

#### Что задаёт человек и что выбирает бот

Человек пишет только программу (`стандарт` / `спорт`), категорию (`взрослые` / `дети`) и количество застрахованных (1–10), в любом порядке; неуказанное — Стандарт, взрослые, 1 человек. Каждый `web ns` выписывает полис.

Остальное бот выбирает сам, каждый раз заново, и пишет выбранное в заголовке отчёта — так за обычные запуски проверяется много комбинаций, а любой результат можно повторить:

- сумма — из справочника НС (`/ns/schema`, 1–3,5 млн с шагом 100 000);
- срок — 12, 6, 3, 1 месяц или 5 дней (произвольный срок не выбирается: он требует ввода дат);
- в Спорте — 1–2 вида спорта из справочника (180 видов) и роль у каждого застрахованного (спортсмен, тренер/судья, параспортсмен).

Застрахованный №1 у взрослых — тестовый клиент из `fixtures/insurance.json` → `client` (он же страхователь), остальные — вымышленные люди с корректными ИИН, которых бот вводит вручную. У детей страхователь — тестовый клиент, застрахованный №1 — тестовый ребёнок (`fixtures/insurance.json` → `child`, если её скан лежит в `data/documents/`), остальные — вымышленные дети 3–17 лет со свидетельством о рождении. Тестового ребёнка нет в ГБД: бот прикладывает скан её паспорта («Приложить документ»), сайт распознаёт данные, бот сверяет каждое поле с настоящими данными, неверные исправляет и записывает ошибкой (на dev распознавание путает местами дату рождения и дату выдачи). Если сайт не может её сохранить (сейчас — не может: отправляет её в ЕСБД как нового клиента), это записывается ошибкой, а её место занимает вымышленный ребёнок. Каждый вручную введённый человек добавляет к прогону 5–10 секунд.

Под параметры подстраиваются и проверки: количество застрахованных на шагах 1 и 3, в расчёте, договоре и карточке; возраст каждого застрахованного против категории; роли застрахованных в Спорте; премия против разбивки калькулятора по каждому человеку. Перед отправкой защита выписки сверяет роль каждого застрахованного по его ИИН.

#### МСТ и МСТ Premium

`web mst [туризм|спорт|студенты|деловые] [0-3|4-74|75+] [1–5]` и `web mst premium [туризм|спорт|деловые] [0-3|4-74|75+] [1–5]` — слова в любом порядке, по умолчанию туризм, 4-74, 1 турист. Каждый запуск выписывает полис. Код — `src/mst/`, покупка идёт общим путём (`src/insurance/purchase.js` → `runPurchase` с набором проверок `MST_KIT` из `src/mst/checks.js`).

- Сам выбирает бот: страну (из 240, сумма — из зоны этой страны), даты поездки (начало в ближайшие 2 недели, 3–30 дней), в Спорте — вид и уровень спорта.
- Туристы: в группе 4-74 первый турист — тестовый клиент (он же страхователь), остальные — вымышленные люди, которых бот вводит вручную латиницей и по-русски. В группах 0-3 и 75+ страхователь не застрахован, все туристы вымышленные.
- «Студенты»: бот прикладывает сгенерированный тестовый PDF как студенческий документ, но сайт после «Создать полис» не даёт выписать такой полис («…выписать пока нельзя») — отчёт показывает это как «Полис не оформлен» с причиной.
- Проверки: что ушло в расчёт на шаге 1 (страна, сумма, даты, число туристов, цель, возраст), шаг 3, защита запроса выписки (`POST /mst/policies`), договор (страна, даты, туристы, их возраст и цель, сумма у каждого, вид и уровень спорта), карточка полиса со снимком, одна цена везде, ЕСБД.
- Найдено при запуске: в МСТ Спорт премия в договоре и после выписки 0 ₸ (у туристов суммы есть); вид спорта сохраняется только в списке договоров; в карточке страна по-английски («Bahrain»), у туристов пустые ФИО и номер паспорта.

`api mst` — МСТ напрямую в сервер, без браузера (`src/mst/api.js`, сценарии — `src/mst/cases.js`, правила — `fixtures/mst.json` → `requirements`):

- калькулятор МСТ и Premium, MA01–MA30 (полисы не создаются): возрастные группы, цели поездки (в Premium без студентов), спорт без вида или уровня, 0/5/6 туристов, сумма из чужой зоны или несуществующая, несуществующая страна, Казахстан, две страны из разных зон, даты в прошлом и наоборот, 365/366 дней, неизвестный тариф; в конце — язык ошибок, один способ отказа, одинаковая цена на одинаковый запрос;
- выписка через сервер, MI01–MI18: 5 правильных заявок (туризм, спорт, Premium, 2 туриста, подмена премии) и 8 неправильных (сумма из чужой зоны, турист дважды, число туристов не совпадает со списком, начало в прошлом, неизвестная цель, Premium со студентами, неизвестная оплата, без туристов). Придуманный турист сначала сохраняется (`kdp/save`), сервер возвращает его номер клиента ЕСБД. Черновик (`draft_id`) сервер не требует.
- Отказ калькулятора бывает двух видов: 4xx или ответ 200 с ошибкой в теле и премией 0 — бот засчитывает оба, но отмечает, что способ не один.
- `api mst тесты` — весь список с ожидаемым результатом, `api mst журнал` / `api mst снять <id>` — незавершённые заявки МСТ через API.
- Перед выпиской `api mst` пересохраняет страхователя в ЕСБД с паспортом, как сайт: у общего тестового клиента тип документа мог остаться «удостоверение» от другого продукта, и тогда сервер отказывает («тип документа должен быть rk_passport, получен rk_id»).
- Тестовый ребёнок: в `web mst … 4-74` с 2 и более туристами она — турист №2 (скан паспорта, распознавание, при неудаче сохранения — вымышленный турист вместо неё), в `api mst` — MI06 «страхователь и ребёнок» (её запись в ЕСБД берётся как есть: пересохранить её `kdp/save` не даёт).
- Найдено через API: калькулятор считает 6 туристов (форма — до 5) и две страны из разных зон как одну; 14 из 17 ошибок калькулятора на английском; сервер выписал полис при `insureds_count` = 3 и одном туристе; премия 0 ₸ у Спорта повторяется и через API; на конфликт номера паспорта в ЕСБД `kdp/save` отвечает 503 вместо понятной ошибки.

#### Как бот подтверждает выписку

1. **Все параметры задаются явно** (программа, категория, количество, сумма, срок, дата начала = завтра) и сверяются с формой и с запросом калькулятора до выпуска. Любое расхождение останавливает сценарий: полис не выписывается.
2. **Запрос выписки проверяется перед отправкой.** Бот перехватывает `POST /ns/policies` в браузере: если тело (вариант, категория, сумма, даты, ИИН страхователя и застрахованных) не совпадает с заданным, запрос не уходит на сервер.
3. **Договор связывается с запуском по ID процесса** из ответа на создание (`process_instance_id` → `/ns/policies/{id}/status` → номер договора и `policy_id`), а не по ИИН и времени.
4. **Проверяются оба участника**: ИИН страхователя и всех застрахованных — в договоре (API) и в карточке договора в браузере (`/policies/{policy_id}`: номер, статус «ОФОРМЛЕН», программа, даты, суммы).
5. **Журнал заявок** (`data/insurance-runs/`, общий для НС и МСТ): ID процесса пишется на диск сразу после отправки, атомарно (черновик → переименование). Запись закрывается только определённым ответом сервера. «Ещё в обработке», ответ сервера 5xx/обрыв связи без ID процесса, недоступный API, а также договоры, найденные лишь по ИИН и времени (тестовый клиент общий — совпадение не доказательство), оставляют её открытой, и новый запуск этого сценария не выполняется. Это касается и негативных сценариев: ошибка сервера может выписать по ним лишний полис. Закрывает запись только ID процесса с итогом или явный отказ 4xx. Повреждённый файл журнала останавливает все выписки. На dev I13, I14 и I16 всегда зависают, поэтому после первого `api ns` они будут заблокированы до ручного снятия. Каждая команда смотрит только свой канал: `web ns` — заявки через сайт (любая открытая блокирует следующую выписку через сайт, с любыми параметрами), `api ns` — заявки через API (блокируется сам сценарий). Список открытых заявок — `web ns журнал` / `api ns журнал`, ручное снятие блокировки — `web ns снять <id>` / `api ns снять <id>` (только если вы уверены, что полис не создан). В Docker и k8s папка смонтирована как постоянная.

#### Как читать отчёт

Отчёт написан для человека, который не знает систему: сначала вывод, потом подробности, без служебных названий проверок.

- **Первая строка — вывод:** «✅ Полис оформлен, новых ошибок нет», «⚠️ Полис оформлен, но есть новые ошибки: 3», «❌ Полис не оформлен» (с причиной) или «❔ Неизвестно, оформлен ли полис».
- **Что делали:** программа, кто застрахован, сумма и срок (их бот выбрал сам), время.
- **Полис:** номер и ссылка на карточку.
- **🆕 Новые ошибки** — о них ещё не сообщали, каждая одним предложением.
- **🤔 Возможно, ошибки** — нарушено правило, которое аналитик ещё не подтвердил.
- **❔ Не удалось проверить** — данных не было или стенд не ответил.
- **📋 Уже известные ошибки** — из `fixtures/insurance.json` и `fixtures/<продукт>.json` → `knownIssues` (поле `plain` — их описание простыми словами).
- **✅ Похоже, исправлено** — известная ошибка в этот раз не повторилась; тогда её можно убрать из списка.

Для `api ns` и `web ns ошибки` вместо «Что делали» — сколько сценариев проверено и сколько полисов выписано.

ЕСБД и тарифы на итог сценария не влияют: успех выписки — статус «Оформлен» и верные данные.

#### Тестовые документы

Сканы документов тестовых людей лежат в `data/documents/` и в git не попадают (`.gitignore`: персональные данные). Сейчас это `test-child-passport.pdf` — паспорт тестового ребёнка (`fixtures/insurance.json` → `child.document_file`). На сервере файл нужно положить туда же; без него бот обходится вымышленными людьми.

Найдено с тестовым ребёнком: распознавание паспорта путает местами дату рождения и дату выдачи (и пишет фамилию в отчество); человека, который есть в ЕСБД, но нет в ГБД, сайт сохраняет как нового клиента — ЕСБД отвечает 503, застраховать его нельзя; в договорах «Дети» (НС) страхователем записан первый ребёнок, а не взрослый. Причина прежней «известной проблемы» «стенд не сохраняет вымышленных детей» — бот выбирал не тот тип документа (в списке «Свидетельство о рождении ребенка»), исправлено.

#### Требования и тарифы

- `fixtures/ns.json` → `requirements` — правила, по которым тесты ждут отказа. Правило с `confirmed: true` (из интерфейса, справочника или подтверждено аналитиком) даёт ❌, неподтверждённое — ❔ с пометкой «правило не подтверждено». Подтвердили правило — поменяйте флаг и укажите источник.
- Отказ засчитывается, только если ошибка называет нужное поле (`expectError` в `src/ns/cases.js`) — и при мгновенном ответе 4xx, и когда процесс завершился ошибкой (`LastError`). Отказ по другой причине, без причины, зависание, 401/403 — «не удалось проверить».
- `fixtures/insurance.json` (общие части сайта) и `fixtures/<продукт>.json` (только этот продукт) → `knownIssues` — известные проблемы: условия, по которым бот узнаёт уже сообщённую проблему и показывает её отдельно от новых.
- `fixtures/ns.json` → `tariffs`: `snapshot` — снимок тарифов с dev, ловит изменения; `approved` — утверждённые тарифы, пока не заданы, поэтому правильность тарифа помечается «не удалось проверить». Согласованность премии во всех местах (калькулятор, форма, окно оплаты, договор, карточка) проверяется всегда.
- Тестовые телефон и email в `fixtures/insurance.json` → `client` пока не согласованы с командой.

К сообщению прикладываются скриншоты сценариев с багами, новыми и уже известными (до 10). На карточке полиса неверные поля обведены красным, в подписи перечислены баги: что видно на снимке и что нет (например, ЕСБД). Если сценарий упал, присылается снимок экрана, на котором он остановился.

Дата окончания полиса считается так же, как на сервере: начало + N месяцев с прижатием к последнему дню месяца, минус 1 день (31.01 + 1 месяц → 27.02). Браузер бота работает в часовом поясе Алматы. Бот рассчитан на один запущенный экземпляр: два бота с разными журналами друг о друге не знают.
